# 并发调模型把线程池打满：`TaskRejectedException` / `RejectedExecutionException`

## 报错原文

如果你给模型调用配了**有界队列**的线程池，过载时会抛这个：

```
org.springframework.core.task.TaskRejectedException: Executor [java.util.concurrent.ThreadPoolExecutor@3f2a1b4c[Running, pool size = 8, active threads = 8, queued tasks = 100, completed tasks = 0]] did not accept task: java.util.concurrent.CompletableFuture$AsyncSupply@7d4b2a1e
```

里层的原始异常是 JDK 的：

```
java.util.concurrent.RejectedExecutionException: Task java.util.concurrent.CompletableFuture$AsyncSupply@7d4b2a1e rejected from java.util.concurrent.ThreadPoolExecutor@3f2a1b4c[Running, pool size = 8, active threads = 8, queued tasks = 100, completed tasks = 0]
```

> `TaskRejectedException` 是 Spring 的 `ThreadPoolTaskExecutor` 自己包的，消息措辞可能因 Spring 版本而异（6.x 里显示的 executor 类型与早版本不同）。搜 `did not accept task` 或 `RejectedExecutionException` 都能定位到同一条。

**但更常见的情况是：什么都不报，只是全线变慢。**

日志里干干净净，接口 RT 从 2 秒涨到 40 秒，最后是上游或网关把它超时掉。查监控能看到 `queue.size()` 一路往上涨。

## 为什么

**大模型调用是「慢 IO」，和普通业务接口根本不是一类任务。**

| | 普通业务接口 | 大模型调用 |
| --- | --- | --- |
| 单次耗时 | 几十毫秒 | 非流式 3–15 秒；流式更长，几十秒到几分钟 |
| 是否可预测 | 基本可预测 | 取决于模型要输出多少字，不可预测 |
| 失败重试 | 便宜 | 贵（一次重试就是再一次十几秒） |

线程数就是你**同时能打出去的模型调用数**。一个 8 线程的池，第 9 个并发请求开始就得排队。默认配置下，两个陷阱一个比一个隐蔽：

### 陷阱一：Spring 默认的 `applicationTaskExecutor` 队列是无界的

`@Async` 不指定 executor 时用的就是它（Spring Boot 自动配置的那个 `ThreadPoolTaskExecutor`）。它的默认值是：

| 参数 | 默认值 |
| --- | --- |
| `corePoolSize` | 8 |
| `maxPoolSize` | `Integer.MAX_VALUE` |
| **`queueCapacity`** | **`Integer.MAX_VALUE`** |

`queueCapacity` 是 `Integer.MAX_VALUE`，所以队列**永远填不满** —— 而 `ThreadPoolExecutor` 只有在队列满的时候才会把线程从 core 扩到 max。结果就是**池永远停在 8 个线程**，多出来的任务无限堆积。

`maxPoolSize=Integer.MAX_VALUE` 在这里是纯摆设，看着很安全，实际一个线程都不会多起。

所以默认配置下**不会**抛 `RejectedExecutionException`，它只会把所有请求吸进队列慢慢等。**这个比报错难查得多** —— 因为报错会告诉你「池满了」，而排队只是让你变慢。

### 陷阱二：自己 new 有界队列的池，就会看到本文开头那个报错

多数人听说「队列不能无界」之后，会改成这样：

```java
new ThreadPoolExecutor(8, 8, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100));   // 现在有界了
```

队列一满，默认的 `AbortPolicy` 立刻抛 `RejectedExecutionException`。**报错终于有了，但请求也挂了。**

### 附带陷阱：`parallelStream` / 无 executor 的 `CompletableFuture` 走的是全局池

```java
// 并行调 3 个模型做投票
List<String> answers = models.parallelStream()
        .map(this::callModel)     // ← 跑在 ForkJoinPool.commonPool() 上
        .toList();
```

不传 executor 的 `CompletableFuture.supplyAsync(fn)` 和 `parallelStream()` 都落在 `ForkJoinPool.commonPool()` 上，而它的并行度是 **`CPU 核数 - 1`**。经验值：一台 2 核 2G 的机器，并行度是 **1** —— 等于没有并发。

更麻烦的是 `commonPool` 是**全 JVM 共享**的。你在这里用它堵住几个阻塞调用，别处（包括某些库内部）用 `parallelStream` 的代码会一起卡住。阻塞型 IO 任务就不该用 `commonPool`。

## 怎么改

### 第一步：模型调用单独一个池，不和业务共用

```java
import org.springframework.scheduling.concurrent.CustomizableThreadFactory;

@Bean("llmExecutor")
public ThreadPoolExecutor llmExecutor() {
    return new ThreadPoolExecutor(
            16,                                    // 常态并发
            64,                                    // 突刺上限
            60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),         // 有界，别用无参 LinkedBlockingQueue
            new CustomizableThreadFactory("llm-call-"),  // Spring 自带的命名工厂
            new ThreadPoolExecutor.CallerRunsPolicy()    // 满了让提交方自己跑
    );
}
```

三个点都在注释里，展开说：

- **队列必须有界。** `new LinkedBlockingQueue<>()` 不传容量就是 `Integer.MAX_VALUE`，和 Spring 默认那个坑一样。
- **线程名要有前缀。** `jstack` / 线程 dump 里看到 `llm-call-3` 卡在 socket read，能立刻确认「是模型调用堵住了」，比看 `pool-3-thread-2` 强太多。
- **拒绝策略别用默认的 `AbortPolicy`。** 并发调模型时，队列满代表已经过载，直接抛异常只会让请求 500。

拒绝策略的取舍：

| 策略 | 过载时的表现 | 什么时候用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException`，请求 500 | 调用方自己有降级/重试逻辑 |
| `CallerRunsPolicy` | 提交任务的线程自己跑，接口变慢但不报错 | 想用背压代替报错 —— 代价是占住提交线程（多半是 Tomcat 工作线程），别在流式场景用 |
| `DiscardPolicy` / `DiscardOldestPolicy` | **静默丢弃任务** | ❌ 别用。调用方永远等不到结果，又是一个「不报错」的坑 |

### 第二步：池上限对着厂商的限额配，不是对着核数配

大模型的并发不是你能随便开的。你开 64 个并发打过去，厂商侧 RPM / TPM 打满，429 直接糊脸 —— 池没满，上游先拒了你。

经验值：先按 **4–8** 起步，压测再往上调，同时盯着上游返回的 429 比例。**池的容量上限应该由「上游能承受多少并发」决定，不是由「机器有几个核」决定。**

### 第三步：池里的每个任务必须有自己的超时

一个卡死的调用会永久占住一个线程，池很快就空了。超时怎么设，见「[流式请求设了总超时](流式请求设了总超时.md)」那条：**连接超时该设、读空闲超时该设、请求总时长对流式不该设**。

### 第四步：要真并发，用显式传 executor 的 `CompletableFuture`

```java
CompletableFuture<ChatResponse> f = CompletableFuture.supplyAsync(
        () -> provider.chat(req), llmExecutor);   // ← 显式传池，别用默认的 commonPool
```

## 怎么预防

**第一条：模型调用的线程池独立命名 + 独立监控。** 光看 `activeCount` 和 `queue.size()` 就够 —— 队列持续大于 0 就是过载的第一信号，比等报错或等超时早得多。

**第二条：不要用 `parallelStream()` 或裸 `CompletableFuture` 做并发模型调用。** `commonPool` 并行度只有核数减一，还是全局共享的，阻塞任务放进去会连累整个 JVM。

**第三条：看到 `queue.size()` 一直涨但 CPU 很低，先怀疑「任务在排队等慢 IO」，不是「程序卡住了」。** 这两者的排查方向完全相反。

**第四条：容量规划从上游反推。** 先确认套餐的 RPM/TPM 能撑多少并发，再决定池大小；反过来定（先按机器核数开池）的结果就是稳定吃 429。

## 环境

| 组件 | 版本 |
| --- | --- |
| JDK | 17 / 21 |
| Spring Boot | 3.x（默认 `applicationTaskExecutor`：core 8、`maxPoolSize` 与 `queueCapacity` 均为 `Integer.MAX_VALUE`） |
| 涉及类 | `ThreadPoolTaskExecutor` / `ThreadPoolExecutor` / `ForkJoinPool.commonPool()` |
| 触发条件 | 并发编排多个模型调用（并行 RAG 检索、多模型投票、批量处理），复用业务线程池或直接用 `commonPool` |
