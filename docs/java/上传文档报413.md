# 上传 PDF 报 413，可应用日志里一条请求都没有

## 报错

同一个根因，三种完全不同的表象 —— 这就是它难查的地方。

**一、请求根本没到你的服务。** 浏览器或客户端拿到的是 Nginx 自己吐的 HTML：

```html
<html>
<head><title>413 Request Entity Too Large</title></head>
<body>
<center><h1>413 Request Entity Too Large</h1></center>
<hr><center>nginx/1.24.0</center>
</body>
</html>
```

关键线索是最后那行 `<center>nginx/1.24.0</center>` —— **这个响应不是你写的**。你的 Spring 应用 access log 里什么都没有，因为请求在代理层就被拒了。

**二、请求到了 Tomcat，被 multipart 解析器拦下。**

```
org.springframework.web.multipart.MaxUploadSizeExceededException: Maximum upload size exceeded;
nested exception is java.lang.IllegalStateException:
org.apache.tomcat.util.http.fileupload.impl.FileSizeLimitExceededException:
The field file exceeds its maximum permitted size of 1048576 bytes.
	at org.springframework.web.multipart.support.StandardMultipartHttpServletRequest.handleParseFailure(StandardMultipartHttpServletRequest.java:127)
```

`1048576` 是 1 MiB，正是默认值。这个异常默认会落成 **500** —— 于是「文件太大」被包装成了「服务器内部错误」，前端弹出「系统繁忙，请稍后重试」，用户会一直重试。

**三、传到一半直接断连。** 客户端看到 `java.net.SocketException: Connection reset` 或浏览器里的 `ERR_CONNECTION_RESET`。

这个形态来自 Tomcat 的 `server.tomcat.max-swallow-size`（默认 2 MB）。请求超限被拒之后，Tomcat 会尝试把剩余的请求体读完再回响应，好让客户端收到正常的状态码；超过 swallow 上限就不读了，直接关连接。所以现象是「稍大的文件报 500，再大一点反而变成断连」—— **同一个原因的两个区间**，特别容易被当成两个 bug 分头查。

## 为什么

### 两层各有一个 1 MB 默认值，而且互不知情

| 层 | 配置项 | 默认值 |
| --- | --- | --- |
| Nginx | `client_max_body_size` | 1 MB |
| Spring Boot | `spring.servlet.multipart.max-file-size` | 1 MB |
| Spring Boot | `spring.servlet.multipart.max-request-size` | 10 MB |
| Tomcat | `server.tomcat.max-swallow-size` | 2 MB |

前两行的 1 MB 是**巧合，不是约定** —— 它们各自独立定的。所以最常见的两种半吊子修法都长这样：

- 只改了 Spring → 大文件仍然被 Nginx 挡住，应用日志还是空的，你以为「改了没用」
- 只改了 Nginx → 请求这次进来了，但换成了 `MaxUploadSizeExceededException`

### 为什么 LLM 项目特别容易撞上这个

RAG 的第一步就是传文档。一份扫描版 PDF 十几 MB 很正常，一份带图的 PPT 也常见，一份 epub 更不必说。

而这类上传接口往往是从「先让 demo 跑起来」的版本直接上的 —— demo 当时用的是自己手写的两页 txt，2 KB。没人会想起来改上传大小，因为它从来没报过错。

还有一笔隐性成本：**multipart 是先收完整个请求体、再进 Controller**。默认配置下，一个 50 MB 的 PDF 会被完整写进临时目录，然后在解析阶段被拒。带宽、磁盘 IO、连接占用全都付了，一个 token 都没生成。

## 怎么改

### 一、两层一起改，写在同一个提交里

`nginx.conf`：

```nginx
server {
    # 放在 location 外面，作用到整个 server
    client_max_body_size 50m;

    location /api/rag/upload {
        proxy_pass http://app:8080;
        proxy_request_buffering on;     # 默认即 on，写出来是为了提醒你它的存在
        proxy_read_timeout 120s;        # 解析大 PDF 常超过默认的 60s
    }
}
```

`proxy_request_buffering on` 的语义是：Nginx 先把整个文件收完，再一次性转给后端。好处是后端不会被慢客户端占住连接；坏处是**大文件白占一次磁盘**。想省这一趟，配 `off` 让请求边收边转 —— 但要同时把后端的连接超时调够，否则慢网络下会变成 `upstream timed out`。

`application.yml`：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 50MB        # 单个文件
      max-request-size: 60MB     # 整个请求：多文件 + 表单字段之和
  tomcat:
    max-swallow-size: 60MB       # 别让「超限」退化成 connection reset
```

`max-request-size` 必须比 `max-file-size` 大一点，多文件场景按「文件数 × 单文件上限」估。两个值一样大时，稍微带点表单字段就会先撞 `max-request-size`，报的还是同一个异常，但你会以为是 `max-file-size` 没生效。

### 二、把「太大」变成你的错误，别让它冒充 500

```java
@RestControllerAdvice
public class UploadExceptionHandler {

    @ExceptionHandler(MaxUploadSizeExceededException.class)
    public ResponseEntity<Map<String, Object>> tooLarge(MaxUploadSizeExceededException e) {
        return ResponseEntity.status(HttpStatus.PAYLOAD_TOO_LARGE)
                .body(Map.of(
                        "error", "file_too_large",
                        "limit", "50MB",
                        "hint", "扫描件请先降采样到 200dpi 以内"));
    }
}
```

两个理由值得写这十几行：默认的 500 会把「文件太大」伪装成「服务器坏了」，用户不会自己想到去压缩；而 413 带上明确上限，第一次就能给出可操作提示。

顺带说一下：这条 `@ExceptionHandler` **只在请求真的进到 Spring 之后才有机会执行**。Nginx 那层的 413 它管不着 —— 所以检查响应体里有没有 `nginx` 字样，是最快的分层判断。

### 三、大文件根本不该走这个接口

这是我最后才想明白、也最推荐的改法。

一个 50 MB 的 PDF 穿过应用服务器，成本是：占一条连接几十秒、占一份临时磁盘、把 Tomcat 的工作线程押在这上面。**而这些成本和「调模型」毫无关系。**

改成直传对象存储：

1. 前端向你的后端要一个**预签名 URL**（S3 / OSS / COS 都支持，有效期几分钟）
2. 前端直接 PUT 到对象存储 —— 完全不经过你的应用
3. 后端只收一个 `objectKey`，由异步任务去拉取和处理

改完之后，应用层的 `client_max_body_size` 可以调回 `1m`，接口只剩 JSON，而且天然支持断点续传和前端进度条。

**什么时候不该这么改：** 内网服务、文件本来就不出机房、单次上传不超过几 MB。这时候为「架构正确」引入对象存储和签名逻辑，成本远高于改两行配置 —— 这个税不值得付。

## 怎么预防

**一、上传大小写进配置，不吃默认值。** 而且必须两层写在同一个提交里。只改一层产生的现象是「改了没用」，这是最容易耗掉半天的形态。

**二、把「请求没到应用」当成一类独立故障来分。** 判据只有一句：**应用日志里有没有这条请求。** 没有 → 代理层；有 → 应用层。这个二分能把排查时间从半小时压到两分钟。想让它更快，给 Nginx 的 error 页加个自定义 header（`add_header X-Gateway nginx always;`），一眼就能确认是谁回的。

**三、上线前用真实文件测。** 用你业务里最大的那个扫描件，别用 2 KB 的 txt。这是唯一能提前撞上这个坑的办法，而且只需要试一次。

**四、413 的比例单独打点。** 它突然上升通常只有两个原因：用户开始传扫描件了（产品侧的正常变化），或者有人改了 `client_max_body_size`（配置漂移）。两者的处置方式完全相反 —— 前者该提示用户，后者该回滚配置。混在一个「错误率」指标里就分不出来了。

## 环境

| 组件 | 版本 |
| --- | --- |
| JDK | 17 |
| Spring Boot | 3.x（内嵌 Tomcat 10.1，Servlet 6） |
| 反向代理 | Nginx 1.24（`client_max_body_size` 默认 1m） |
| 触发条件 | 默认配置下上传超过 1 MB 的文件 |

> `max-file-size` / `max-request-size` 的默认值在 Spring Boot 各版本间是稳定的（1 MB / 10 MB），但 `MaxUploadSizeExceededException` 的嵌套措辞、以及默认返回的状态码，随 Spring 版本存在差异 —— 以你实际用的版本行为为准。
