# 流式请求设了 `timeout`，回答说到一半就断

## 现象

```
java.net.http.HttpTimeoutException: request timed out
```

或者更隐蔽的形式 —— **不报错，但回答只输出了一半就停了。**

代码看起来很正常：

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.deepseek.com/v1/chat/completions"))
        .timeout(Duration.ofSeconds(30))     // ← 就是这一行
        .header("Authorization", "Bearer " + apiKey)
        .POST(HttpRequest.BodyPublishers.ofString(body))
        .build();
```

问「1+1 等于几」没问题。问「帮我写一份详细的技术设计文档」，答案就断在中间。

## 为什么

**`HttpRequest.timeout()` 是「整个请求」的超时，不是「迟迟没响应」的超时。**

它从请求发出开始计时，**包含读取响应体的全部时间**。对普通接口这是合理设计；对流式接口就是灾难：

| | 普通接口 | 流式接口 |
| --- | --- | --- |
| 响应耗时 | 通常 < 1 秒 | **可能持续几十秒到几分钟** |
| 耗时是否可预测 | 可预测 | **不可预测，取决于模型要输出多少字** |
| 设 30 秒固定超时的后果 | 基本不会触发 | 回答还在生成时被硬中断 |

**流式接口的耗时本质上是「不知道的」** —— 你没法预判模型会写多长。用固定值去卡它，长回答必然被切。

更麻烦的是**这个报错不一定出现**：如果客户端把「流中断」当成正常结束处理，你只会看到「回答不完整」，日志里干干净净。用户投诉「AI 答到一半就不说了」，而你查不到任何异常。

## 怎么改

### 核心思路：把「超时」拆成两类

| 超时类型 | 管什么 | 该不该设 |
| --- | --- | --- |
| **连接超时** | 连不上上游，多久放弃 | ✅ 应该设，5 秒左右 |
| **读空闲超时** | **多久没收到新数据**算异常 | ✅ 应该设，按业务定 |
| 请求总时长 | 这次请求一共花了多久 | ❌ **流式请求不该设** |

```java
HttpClient http = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))    // 连接阶段，该设
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.deepseek.com/v1/chat/completions"))
        // 关键：这里不调 .timeout()
        .header("Authorization", "Bearer " + apiKey)
        .POST(HttpRequest.BodyPublishers.ofString(body))
        .build();
```

### 「上游卡住不返回数据」怎么兜底

靠**读空闲**判断 —— 不看「总共花了多久」，只看「多久没有新数据」。

在读取循环里自己计时：

```java
long lastChunkAt = System.nanoTime();
long idleLimit = Duration.ofSeconds(60).toNanos();

http.send(request, HttpResponse.BodyHandlers.ofLines())
        .body()
        .forEach(line -> {
            long now = System.nanoTime();
            if (now - lastChunkAt > idleLimit) {
                throw new IllegalStateException("上游超过 60 秒没有新数据，判定为卡死");
            }
            lastChunkAt = now;

            // ... 正常处理这一行
        });
```

判断逻辑的区别：

- **已经吐了 3 分钟但还在持续输出** → 正常，不该中断
- **60 秒一个字都没吐** → 基本可以确定上游挂了，该中断

### 各客户端的超时语义对照

| 客户端 | 哪个参数是「两次数据之间的间隔」 | 能用吗 |
| --- | --- | --- |
| `OkHttp` | `readTimeout` | ✅ 语义正确，但要设得足够大（如 5 分钟） |
| `Apache HttpClient` | `setSocketTimeout` | ✅ 同上 |
| `java.net.http.HttpClient` | 无直接等价项 | ⚠️ 需自己实现空闲检测 |
| `HttpRequest.timeout()` | ❌ 是「总时长」 | ❌ 流式场景禁用 |
| `WebClient.responseTimeout()` | ⚠️ 作用于整个响应 | ❌ 流式场景慎用 |
| `RestTemplate` | 不支持流式 | ❌ 别用它做流式 |

> **用之前先确认语义。** 同样是叫 `timeout`、`readTimeout` 的参数，在不同客户端里含义完全不同 —— 这是流式接口最容易被误导的地方。

## 怎么预防

**第一条：区分「连接慢」和「出字慢」。** 前者该有超时，后者不该。

**第二条：流式接口必须有「读空闲」监控。** 判断标准是「多久没数据」，不是「总共多久」。

**第三条：上线前用长回答测一次。** 让模型写个 1000 字的东西，看会不会断在中间。**短问题永远测不出这个 bug。**

**第四条：和网关的超时一起改。** 应用层设对了，Nginx 的 `proxy_read_timeout` 默认 60 秒照样会切长回答。两边都要看。

**第五条：日志里记录「实际耗时」。** 如果发现一堆请求的耗时都精确地等于你设的超时值，那就是被超时切了，不是模型慢。

## 环境

| 组件 | 版本 |
| --- | --- |
| JDK | 11+（`java.net.http.HttpClient`） |
| 客户端 | `HttpClient` / `WebClient` / OkHttp 均可复现 |
| 复现条件 | 给流式请求设了 30 秒左右的固定超时，然后让它输出长回答 |
